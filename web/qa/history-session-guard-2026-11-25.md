# 기록 조회·삭제: 기존 세션 소실 방어

## 제품 변경

`listDecisionHistory()`와 `deleteDecision()`에서 기존 세션만 확인한다. 기록 조회 중 세션이 없으면 새 익명 가입·데이터 조회 없이 빈 목록을 반환한다. 삭제 중 세션이 없으면 RPC 전 `AUTH_REQUIRED`로 종료한다. 기존 화면의 오류 경로가 표시 기록·저장한 회고·회고 초안·관련 결정 초안을 보존한다.

기존 세션 읽기 오류는 그대로 전파한다. 인증 조회 직후 deadline 취소 상태를 확인하므로 제한시간이 지난 뒤 조회·삭제를 시작하지 않는다. UI·스타일·저장 모듈·스키마·권한·기존 운영 함수는 변경하지 않았다.

## 실제 검증

수정 전 실제 HistoryScreen·API·세션 helper·저장 모듈과 모의 Supabase SDK를 사용해 오류를 재현했다. 목록 표시 후 세션을 잃고 삭제를 확인하자 저장 회고가 지워져 새 회귀 테스트가 실패했다.

수정 후 Node **24.22.3** / Vitest **3.2.7**에서 관련 **10개 통과**, 같은 두 파일의 무관한 **37개는 제외**했다. 새 회귀는 화면 기록, 저장 회고, 회고 초안, 연결된 결정 초안이 유지되고 삭제 RPC·익명 가입·실제 네트워크 호출이 없음을 확인했다. 조회 null 분기, 인증 조회 오류, 조회·삭제 deadline, 기존 pagination·삭제 응답 처리도 확인했다.

기존 의존성을 재사용했다. 전체 테스트·로컬 전체 타입 검사·웹 빌드는 반복하지 않았다. 별도 검토자가 세 파일의 diff를 읽고 이번 범위의 차단급 문제 없음으로 확인했다.

출시 입력 162개 중 기존 2개 변경·새 회귀 파일 1개 추가로 총 **163개**다. 나머지 160개 입력의 바이트는 같다. 새 소스 목록 SHA-256: `36ff10f173297eb7e10ed3f5836cf7595af56d11de3d863aa63c619da62a8aed`.

## 한계와 서버 차단점

이 수정은 **기존 세션이 없는 경우**를 다룬다. 화면 표시 후 다른 유효 세션으로 바뀌는 사례와 기존 void 삭제 RPC의 실제 삭제 건수·완전한 소유권 확인은 별도 한계다. 전체 Auth 사용자 삭제나 제공자 보관 조건을 해결한 것으로 보지 않는다. 실제 Supabase·실물 기기·Node 22 결과도 아니다.

기존 마이그레이션 요청의 기록 상태는 `prepared-not-yet-returned`이며 제공자 요청 ID·종료 결과가 없다. 현재 연결 기능에 해당 요청의 상태 조회·재개 기능이 없으므로 동일 apply를 반복하지 않았다. 실행 호스트 cell ID는 Supabase 작업 ID가 아니다. 다음 서버 단계는 기존 요청의 실제 전달 여부와 종료 상태를 추적할 수 있는 실행 진단 결과 확보다. 새 SQL이나 두 번째 마이그레이션은 요청하지 않았으며 지원 메시지도 보내지 않았다.
