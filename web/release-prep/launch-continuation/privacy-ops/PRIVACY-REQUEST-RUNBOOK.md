이미 있는 공유 링크나 신고 접수번호는 **선택적 대상 참고자료**다. 문의를 위해 새 링크를 만들거나 AI 결정을 추가 생성하게 하지 않는다. 원문 선택지·상황 전체, 이름·전화번호·계좌·건강정보, 신분증·여권, 비밀번호·인증번호·로그인 토큰·기기 저장소 전체를 요구하지 않는다. 첨부가 필요하면 관련 없는 내용이 가려진 최소 화면만 사용한다.

### 내부 접수 기록

담당자는 문의를 실제 확인한 뒤 내부 지원번호를 배정한다. 예: `SUP-YYYYMMDD-001`. 이 번호는 **이메일 지원 문의번호**이며 앱 서버의 신고 접수번호가 아니다.

최소 처리표에는 지원번호, 접수일, 요청 종류, 원래 기기 접근 여부, 확인 방법, 승인된 범위, 처리 상태, 결과·통지일, 다음 확인일만 남긴다. 이메일 원문·민감한 상황 설명·인증정보를 처리표에 다시 복사하지 않는다. 실제 대상 식별자가 필요하면 접근 제한된 참조로 관리하고 일반 보고서에는 넣지 않는다.

신분증·민감한 첨부가 먼저 도착했다면 회신에 재첨부하지 않는다. 필요한 최소 사실만 분리하고 불필요한 자료는 정리 대상으로 표시한다. 메일 및 별도 내려받은 복사본의 정리는 채택된 절차에 따라 확인하며, 제공자의 내부 보관까지 없다고 약속하지 않는다.

### 추가 개발이 필요한 확인 방식

현재 세션이 살아 있어도 이메일과 그 세션을 안전하게 연결하는 일반 지원용 확인 기능은 없다. 이를 지원하려면 다음과 같은 작은 서버 기능을 별도 구현·검증한다.

1. 사용자가 앱에서 요청 종류와 범위를 확인하고 명시적으로 제출한다.
2. 서버가 인증된 사용자 식별자를 직접 얻고 요청 범위를 검증한다. 클라이언트가 보내는 사용자 ID를 신뢰하지 않는다.
3. 서버에 요청자·대상·허용 범위·제출 시각과 처리 상태를 저장하고 비밀이 아닌 접수 참조번호를 돌려준다.
4. 운영자는 서버에 기록된 **실제 인증 요청**과 범위를 확인한다. 참조번호를 아는 사실만으로 권한을 확대하지 않는다.
5. 요청 범위 변경·추가 삭제는 원래 앱에서 다시 확인한다. 결과는 같은 인증 상태에서 조회할 수 있게 한다.
6. 이메일 수집을 추가한다면 목적·보관·동의/고지 변경을 함께 검토한다. 로그인 토큰을 메일로 보내는 방식은 사용하지 않는다.

이 기능은 설계 제안이며 현재 구현·운영 완료로 안내하지 않는다. 확인을 위해 새 유료 AI 호출이나 가짜 결정·투표를 만들게 하지 않는다.

## 5. 유형별 처리 지침

### A. 작성한 결정이 보이고 직접 지우려는 경우

1. 원래 앱·브라우저를 유지하도록 안내한다.
2. **결정 기록 전체 보기 → 대상 기록의 삭제 → 확인 → 새로 고침** 순서를 안내한다.
3. 결정과 연결 친구 투표, 이 기기의 관련 회고·초안 범위를 설명한다.
4. 사용자에게 목록에서 사라졌는지와 기기 정리 오류 유무만 묻는다. 선택지 원문 전체는 받지 않는다.
5. 사용자가 직접 확인했다면 `self_service_reported_complete`로 기록한다. 운영자가 서버 전체를 검증했다고 쓰지 않는다.

### B. 삭제 오류 또는 일부만 지워진 경우

- 삭제 완료를 확인하지 못했다는 메시지면 먼저 새로 고침으로 확인하도록 한다. 동일 요청의 재시도가 필요한지 분리한다.
- 서버 결정·투표는 삭제됐으나 기기 회고/초안 정리가 실패했다고 표시되면 **이용 안내**의 기기 삭제 기능으로 안내한다.
- 서비스 전체 오류 여부는 별도 기술 검토로 넘기되, 운영자가 사용자 토큰을 전달받아 대신 로그인하지 않는다.
- 개별 건의 추가 운영 처리가 필요하면 인증된 대상·권한 확인 및 구체적 범위 승인을 선행한다. 성공 응답만으로 완료 통지하지 않는다.

### C. 원래 기기·세션을 잃은 경우

- 앱 재설치·브라우저 초기화를 먼저 요구하지 않는다. 그것으로 이전 익명 상태가 복구된다고 안내하지 않는다.
- 이메일·제목·링크만으로 기록을 찾아 내용을 보내거나 삭제하지 않는다.
- 요청 자체는 접수하고 확인 가능한 범위·필요한 대안을 안내한다. 현재 기술상 안전한 연결 확인 수단이 없으면 그 한계를 정확히 통지하고 담당 검토를 이어 간다.
- 결정의 기존 자동 정리 기준은 설명할 수 있지만 이를 요청에 대한 조사·처리 의무의 대체나 계정 전체 삭제 완료로 쓰지 않는다.
- 글에 본인 개인정보가 노출됐다는 경우에는 아래 E로 별도 검토한다. “작성자가 아니므로 처리 불가”라고 일괄 종결하지 않는다.

### D. 기기의 회고·초안, 친구 투표, 인증 식별자 전체

|---|---|---|

| 자동 생성 식별자·모든 연결 정보 | 일반 문의로 접수하고 범위 확인 | 앱별 데이터·다른 이용자 투표·기존 미니앱·인증 세션·제공자 기록 영향까지 검토한 별도 구현/승인 |
| 열람·정정·처리정지 | 개인정보 권리 요청으로 분류, 실제 범위와 기한 검토 | 이메일만으로 다른 사람의 기록을 내보내지 않음. 없는 수정·내보내기 기능을 있다고 안내하지 않음 |

### E. 공유 질문·AI 결과·개인정보 노출 신고

1. 앱 이름, 이미 있는 대상 링크 또는 접수번호, 신고 범주, 문제가 된 부분의 최소 설명을 받는다.
2. 질문의 개인정보·괴롭힘 등은 작성자 소유권 확인과 별개로 검토한다. 신고자 정보는 상대방에게 전달하지 않는다.
3. 기준은 현재 공유 콘텐츠 이용정책이다: 타인 개인정보·비밀/권리 침해, 혐오·괴롭힘·협박, 성적 착취·아동 유해 내용, 불법 조장·스팸 등. AI 의견에 동의하지 않는다는 사실만으로 위반 확정하지 않는다.
4. 사실 확인 전에는 삭제 완료·계정 제재를 약속하지 않는다. 공개된 내용 확인에 필요한 최소 범위로 제한하고 신고 내용을 AI에 재전송하지 않는다.
5. 앱에서 접수번호가 없거나 신고 기능 오류가 났다면 **이메일 지원 문의가 접수된 것**과 **앱 서버 신고가 접수된 것**을 구분한다. 적용 여부가 확인되지 않은 신고 백엔드가 작동한 것으로 표시하지 않는다.
6. 위반이 확인되면 실제 이용 가능한 조치와 대상 범위를 작성하고 운영 승인을 받는다. 공유 중단·삭제·이용 제한은 현재 서버 기능과 영향 검토를 확인한 경우에만 실행한다.
7. 결과에는 검토 여부와 공개할 수 있는 조치만 알린다. 상대방 식별자·다른 신고 내용·내부 보안정보를 통지하지 않는다.
8. 이의제기는 같은 지원번호로 받으며 원결정의 근거를 다시 검토한다.

## 6. 전체 계정 삭제에서 금지할 지름길

기준 커밋 `ab960b8…`의 `20260929093527_bc_retention_and_account_delete.sql`을 확인했다. **bc_delete_account()는 현재 인증 사용자의 auth.users 행을 삭제한다.** 새 VS 스키마도 작성자·투표자에 auth.users cascade FK를 둔다.

따라서 이 기존 RPC를 “결정해지니 삭제 문의 처리”에 무조건 재사용하지 않는다. 같은 사용자 ID에 연결된 VS 데이터·구 미니앱 데이터, 해당 작성자의 질문에 달린 타인의 투표까지 연쇄 영향이 생길 수 있다. 앱별 범위·연결 대상·현재 배포 정의를 확인하지 않은 상태에서 Auth 사용자 삭제나 모든 익명 사용자 일괄 정리를 권고하지 않는다.

전체 삭제를 별도 구현하더라도 기존 접근 토큰과 세션 종료의 처리 범위까지 확인해야 한다. Auth 사용자 삭제만으로 이미 발급된 모든 토큰이 즉시 무효가 된다고 보장하지 않는다. [S1]

## 7. 결과 통지의 기준

모든 결과 회신은 다음을 구분한다.

- 요청받은 범위
- 실제로 확인·처리한 범위와 확인 시점
- 완료 여부를 확인하지 못한 범위
- 남는 정보와 실제 사유·기간이 확인된 경우 그 내용
- 사용자가 다음에 할 수 있는 동작 및 이의제기 방법

“모두 삭제 완료”는 모든 범위의 근거가 있을 때만 쓴다. 기본 결과값은 `complete_for_confirmed_scope`, `partial`, `not_executed_pending_verification`, `self_service_reported_complete`, `reviewed_no_action` 중 하나다. 문의를 닫더라도 미해결 범위를 숨기지 않는다.

실제 대외 법정 통지는 적용되는 서식·요건을 따르고, REPLY-TEMPLATES.md는 안내 초안으로 사용한다.

## 8. 기한·보관 원칙과 운영 선택 현황

법정 개인정보 정정·삭제 요구에는 요청 조사·필요한 조치와 결과 통지가 요구된다. 현행 시행령 제43조는 해당 정정·삭제 결과 통지의 10일 규정을 두며, 제46조는 본인 또는 정당한 대리인 확인을 요구한다. 법 제38조는 접근 가능한 요구·이의제기 절차를 두도록 한다. **이 규정은 “어떤 문의든 10일 안에 모든 백업까지 삭제”라는 자체 SLA가 아니다.** 사건 종류·접수일·적용 규정을 확인하고 별도 기한을 기록한다. [L1][L2][L3]

문의 원문·첨부와 최소 처리표의 보관을 구분한다. 목적이 끝나 불필요해진 정보는 정리하며, 별도 법령 보존이 필요한 항목은 실제 근거·대상·기간을 기록한다. 운영 편의상 임의의 “법정 5년” 등을 붙이지 않는다. [L4]

OPERATOR-DECISIONS.md의 **최초 답변 1영업일 목표는 사용자 선택으로 확정**했다. 접수·분류와 필요한 최소 보완 안내에 적용하는 목표이며 전체 데이터 삭제 완료기한을 뜻하지 않는다. 담당자와 최소 처리표의 30/90일 보관안은 아직 선택되지 않았고 해당 필드는 null이다. 영업일 달력·운영 시간대·시행일도 미확정이다. 법정기한이나 개별 삭제 요청을 이 숫자로 일괄 연장·거절하지 않는다.

## 9. 실제 운영 시작 전 갖춰야 할 것

- 담당과 열람 권한, 확정된 첫 응답 목표의 영업일·운영 시간 기준, 최소 처리표 보관안 정리
- 이메일 지원번호와 앱 신고번호를 구분하는 처리표
- 본인 직접 삭제 안내 및 오류·접근 상실·신고 답변 준비
- 수동 운영 삭제가 필요한 경우의 인증된 요청 근거·대상 확인·승인·검증 경로
- 신고 서버의 실제 접수 및 운영자의 검토 경로 확인
- 계정 생성/삭제에 대한 최종 Play 답변과 서비스의 실제 범위 일치

Google의 계정 삭제 요건이 적용되는 경우 이메일도 요청 경로가 될 수 있으나 실제 처리 절차가 필요하다. 외부 요청을 앱 재설치에만 의존하도록 만들지 않는다. 이 문서는 자동 익명 인증이 곧 면제라는 결론도, 전체 계정 삭제 의무가 무조건 있다는 결론도 내리지 않는다. [G1]
